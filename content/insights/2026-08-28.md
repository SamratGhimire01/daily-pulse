# Developer Insight

## Topic

Git Rebase vs. Merge for Feature Branches

## Explanation

When integrating changes from a base branch into your feature branch, `git merge` creates a commit that explicitly documents the convergence, preserving exact history. Conversely, `git rebase` rewrites your feature's history by moving its starting point to the tip of the base branch, resulting in a clean, linear commit log. While linear histories are easier to read, rebasing public branches shared with teammates can corrupt their local history and cause severe merge conflicts.

## Practical Example

To safely update your current feature branch with the latest changes from main using a linear history:

```bash
git checkout feature-branch
git fetch origin
git rebase origin/main
```

If conflicts arise, resolve them, run `git add <file>`, and continue the rebase with `git rebase --continue`.

## Takeaway

Use `git rebase` locally to keep your private feature branch clean before opening a pull request, but stick to `git merge` for shared branches where rewriting history will disrupt your team.
